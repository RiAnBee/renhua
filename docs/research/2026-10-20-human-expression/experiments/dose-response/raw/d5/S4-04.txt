线上日志排查最容易陷入一个误区：看到错误日志就开始逐行搜索，却没有先确认故障的时间范围、症状边界和证据是否完整。23:41，服务 P99 从 120ms 升到 4.8s，值班期间我先从 Nginx access log 观察请求是否普遍变慢，再对照 Go 1.21 服务日志和 MySQL 8.0 相关指标，确认问题并不是单个接口异常，而是请求在服务内部出现了持续等待。

当时日志采样率为 1/100，关键请求恰好没有样本。已有日志里只能看到部分请求耗时上升，却无法通过完整调用链还原一次请求从 Nginx 进入 Go 服务、获取数据库连接、执行 SQL 到返回响应的过程。这个现象提醒我们，日志“存在”不等于证据“足够”。采样日志适合观察趋势和常见错误，却不适合承担故障定界，尤其是在高延迟问题中，最需要分析的往往正是少量异常请求。

排查过程中，我把日志中的请求耗时、接口路径和错误信息按故障时间对齐，同时检查连接池状态。由于服务拓扑和连接池配置项已经明确，重点不应停留在“数据库是否变慢”，而要继续确认应用是否能够正常取得连接。最终发现连接池上限 20 被打满，请求在等待可用连接，等待时间逐步反映到整体延迟中，因此 P99 从 120ms 快速升到 4.8s。这个结论也解释了为什么日志中未必出现明显的 SQL 错误：数据库连接本身没有必然失败，应用可能只是长时间拿不到连接。

故障期间不能重启，只能摘流量，所以处理重点不是通过重启清空连接池，而是降低进入异常实例的请求量，避免等待继续堆积。摘流量后，需要持续观察 Nginx 请求延迟、Go 服务处理耗时和连接池使用情况，确认请求等待是否下降，再逐步恢复流量。这个过程要求日志和指标结合使用，单看访问日志只能看到结果，单看连接池状态也无法判断用户请求是否已经恢复。

复盘时最需要修正的不是某一条查询语句，而是证据采集策略。采样率不改，下次同类故障仍然查不到证据。后续应为高延迟、连接池耗尽、请求超时等关键场景保留足够的诊断信息，并确保请求标识能够贯穿 Nginx、Go 1.21 和 MySQL 8.0 相关日志。普通请求可以继续采样，但异常请求应尽量完整记录，至少保留能够定位等待阶段的信息。这样既能控制日志量，又能在故障发生时回答最关键的问题：请求慢在哪里、等待了什么、资源为何耗尽，以及摘流量后是否真正恢复。
