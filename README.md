# 人话 · renhua

中文 | [English](README.en.md)

模型起的中文稿，常见的不是错字，而是句子看着完整，却没落到这次要说的事上。renhua 先看它在和谁说什么、要让对方做什么，再只改妨碍理解和沟通的地方。原稿要说的事和说话的分寸，留给原作者。

它不猜稿子由哪个模型写成，也不拿检测分数当效果。

## 怎么用

把稿子交给支持 Agent Skills 的工具：

```text
用 renhua 把这段改自然，保留我的口吻，只给改稿。
这是写给客户的邮件，去掉模板腔，不要把商量改成催促。
整理这份技术说明的措辞，代码、参数和步骤编号不要动。
```

默认只交完整改稿。想要理由就说“附关键改动说明”。原稿已经自然，就原样还回去，不必凑改动。

不用交代原稿是哪家模型写的。用途、读者、风格样本说清楚了就按它办；没说清，沿用原稿的正式程度、人称和地域词。不翻私人文件，不建作者画像。

## 编辑范围

- 没有作用的重复解释、预告和自我评价。
- 被名词结构压住的动作、错位的修饰、指代不清带来的费解。
- 堆在一起遮住关系的连接词；断句把因果或并列改错了地方。
- 抢过内容的修辞：连续翻案、均匀金句、空泛比喻、重复强调。

长句短句、排比问句、比喻、正式措辞都不是修改理由。不设句长、密度、改动量配额。

## 动手之前

先看这句话在替谁、对谁、为哪件事承担什么：它指向哪个对象，声称了什么，和前后句是什么关系，读者读完要能判断或做什么。缺材料只指出缺口，不替作者补。

改稿不是先找禁词。`满`、`而`、`不是……而是……`、标题和总结都可能有用；只有当表达可以套到任何主题、没有承诺对象，也不承担关系、礼貌、范围、立场或体裁功能时，才考虑改。段首和段末只是优先取样位置。

先处理命题、关系、承诺和读者状态，最后才调词序、句法、标点和节奏。通知、新闻、理论文章、技术帖和随笔各有常态，不把一种体裁改成另一种。

稿件缺用途、材料或责任边界，交稿时指出缺哪样，不用形容词填上。

字可以换，意思不行。数字、术语、引语、来源、限定、立场、责任和请求力度都要留住。有的句子没有新事实也有用：它在回应担忧、交还决定权，或者就是节奏。

### 一个边界例子

> 小组完成了对值班安排的调整。如果方便，请周三前告诉我；来不及也请说一声。

改成：

> 小组调整了值班安排。如果方便，请周三前告诉我；来不及也请说一声。

前一句能简，后一句的宽限不能动：改成“请于周三前提交”，商量就成了催促。这是说明边界的例子，不是效果统计。

## 默认范围

| 可做 | 不自动做 |
|---|---|
| 保义换词，调词序、语法、句子断合 | 补事实、数据、经历、动机或新观点 |
| 改普通说明段落，文件叫 README 也照改 | 动代码、参数、原话、义务、条件或来源 |
| 收敛没有功能的重复加粗 | 改章节层级、步骤编号、表格或交叉引用 |
| 看出组织问题，给一句建议 | 重排、拆合段落，改论证或叙事揭示顺序 |

要重构就直说，仍只用原有材料。说“只改错字”“只审不改”或“保持格式”的，就只做那一件。

中英混排的稿子只动中文部分；纯英文不套中文建议。简繁、地域词、人称跟原稿走。

## 安装与更新

安装时复制整个目录，`references/` 也要带上：

```bash
git clone https://github.com/RiAnBee/renhua.git
mkdir -p ~/.claude/skills
cp -r renhua/skills/renhua ~/.claude/skills/
```

也可以放进你那个工具认的 skills 目录。装过旧版的，先把旧 `renhua` 目录挪走再复制，别让两套规则混在一起。用软链接指向仓库的，更新仓库文件就等于更新安装。

插件入口：

```bash
omp --plugin-dir ./renhua
```

命令入口在 `commands/renhua.md`，只转到核心，不另存一套规则。仓库没有配置插件市场，安装以本地目录为准。

## 旧版撤回了什么

旧版把“不加事实”执行成“不许替换”，还用句长、人机词频和规则命中数管着改稿。这些处方在 2026-09 撤掉了：**能分辨来源，不等于删掉这些特征之后文章更好。**

[LAMP](https://arxiv.org/abs/2409.14509v5) 里职业编辑的动作有大量替换，支撑不了“只删不换”；[StoryScope](https://arxiv.org/abs/2604.03136v6) 研究的是叙事区分信号，用它的分类结果证明结构编辑无益是越界的。中文问答、新闻翻译、语体研究也凑不出一个通用句长。

完整依据在证据摘要里。旧研究留着供复核；“未复现”不写成“永远不能改”，历史小样本的比例也不当成今天的误删率。

## 验证与局限

看一份改稿，先问有没有动到含义、语气或承诺，再问这版是否配得上这次用途。这两个问题之外，改动数量、来源标签、检测器分数都只是旁证。

开发材料包含合成稿，只用于压测编辑边界，**不是人类语料基线，也证明不了真实世界里的效果**。直接提示、真实加载 skill、模型辅助审查和真人评审必须分开报告。

本地研究支持一个较窄的判断：情境骨架和真实材料会改变模型的内容选择，体裁提示会改变形式原型；但这不等于“AI 味”有一套固定词表，也不等于改完必然更像人。当前方法把根因工作假说写成**情境化承诺链断裂**：先核对对象、命题、关系、读者任务和后果，再动形式。

研究仍没有中文完整整稿的编辑干预与真人盲评。强风格、法律和专业内容由作者或实际使用者复核；材料缺了只能指出缺口，不能替作者补事实。改动数量、来源标签和检测器分数都不能替代这项复核。
